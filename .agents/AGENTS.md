- [세션 시작 및 작업 이력 관리 규칙] 새로운 세션을 시작할 때는 항상 `docs/work_history.md`를 가장 먼저 읽어 이전 진행 상황과 현재 상태를 파악하고 업무를 끊김 없이 자연스럽게 이어가십시오. 주요 작업을 완료하거나 상태가 변경될 때마다 날짜와 시간 순으로 작업 내용, 변경점, 다음 계획을 `docs/work_history.md`에 누적 갱신하여 문서화하십시오.
- [언어 규칙] 모든 설계 문서, 구현 계획, 설명 및 작업 내역은 항상 한국어(Korean)로 작성하십시오.
- [채팅창 수식 및 텍스트 표기 규칙] 채팅창 응답 시 LaTeX 문법(\(...\), $$...$$, \mu, \text{}, \approx, \rightarrow 등)은 IDE 채팅창 렌더러에서 변환되지 않고 깨져서 표시되므로 절대 사용하지 마십시오. 단위, 경로, 수식은 사람이 직관적으로 바로 읽을 수 있는 일반 텍스트 및 기본 마크다운 형태로 작성하십시오.
- [사전 승인 철칙] 소스 코드 수정, 패키지 의존성 변경, 주요 아키텍처 변경을 임의로 먼저 수행하여 사후 보고하지 마십시오. 반드시 변경 구상과 작업 방안에 대해 사용자의 명시적인 사전 컨펌(승인)을 받은 후에만 실제 코드 수정을 진행해야 합니다.
- [ROS 환경 로드 규칙] ROS 2 및 관련 빌드/노드 실행 명령어를 수행하기 전에는 항상 `get_ros` 알리아스 또는 ROS 2 Jazzy 환경을 로드해야 합니다. (예: `bash -ic 'get_ros && ...'`)
- [Git 브랜치 및 저장소 관리 규칙]
  - 공식 원본 브랜치(`jazzy` 또는 `main`)는 임의로 수정하지 않고 항상 깨끗한(clean) clone 상태를 유지하십시오.
  - 모든 로컬 작업, 기능 추가, 커스텀 설정은 작업 브랜치(`demo_test` 등)에서 진행해야 합니다.
  - 작업 내용은 적절한 시점에 의미 있는 단위로 커밋하고, 푸시(Push)할 때는 반드시 본인의 개인 Fork 원격 저장소(`my-fork`)로 진행하십시오.
- [프로젝트 실행 및 문서 관리 규칙] VM 환경(IP: 192.168.10.100 등), 포트포워딩, Headless 시뮬레이션, API 서버/대시보드 실행 방법 등 환경 설정이 변경되거나 추가될 경우 `ln_my_command.md` 가이드 문서를 항상 최신 상태로 갱신하십시오.
- [모노레포 및 패키지 관리 규칙] 이 프로젝트는 `pnpm` 기반의 모노레포(`packages/` 하위 모듈: `api-server`, `rmf-dashboard-framework`, `api-client` 등) 구조입니다. 패키지 설치나 스크립트 실행 시 workspace 설정을 존중하고 불필요한 전역 수정이 발생하지 않도록 주의하십시오.
